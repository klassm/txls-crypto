Summary

Yes — and it's better than expected. Three findings:

  1. Auto inventory updates already exist in TXLS. We have a full Bitpanda API-sync stack (daily cron sync, encrypted API keys, holdings rebuild). The premise "manual CSV import only" is outdated — TradeRepublic is CSV-only, but Bitpanda already syncs via API.
  2. The known gap is staking rewards — the legacy Bitpanda API we use today (api.bitpanda.com/v1) does not expose them, so reward-type inventory entries must come from CSV or manual entry (see the gap card).
  3. Bitpanda's new Public API closes that gap — its unified GET /v1/operations endpoint returns all transaction types including rewards and staking. And because the legacy API is decommissioned on 31 Jan 2027, migration to the new API is mandatory anyway — we can gain staking rewards in the same change.

The gap: staking rewards are not in the API sync

manual workaround today

The Bitpanda client's own config (server/src/providers/bitpanda/config.ts) documents that staking rewards are not available via API sync: /trades only covers buy/sell/staking types and wallet transactions only cover deposits/withdrawals. The app therefore instructs users to import rewards via CSV or the manual staking-entry endpoint (POST /:id/transactions, supportsManualStaking in the provider registry). The CSV importer has a proper reward type mapping — the API path is what's missing it.

New Public API — endpoints relevant to TXLS

The new API consolidates wallets, fiat wallets and trades into unified entities and adds portfolio history and Earn management. Scopes are assigned per API key in Account Settings → API: Balances Transaction Trade (Read/Write) Earn (Read/Write) — prices, assets and currencies work with any key.

EndpointScopeRelevance to TXLS
GET /v1/operations Transaction The core endpoint for us. Unified timeline of all historical movements — trades, deposits, withdrawals, rewards and staking. Filters: from/to (date-time), asset_id[], currency_id[]; cursor pagination. Each operation carries operation_type, and per-transaction: transaction_type, flow (INCOMING/OUTGOING), asset_amount, fee_amount, credited_at, asset_balance_after, and for trades rate / to_eur_rate.
GET /v1/portfolio Balances Unified holdings view (replaces /wallets, /fiatwallets, /asset-wallets) — EUR-valued. Ideal as a reconciliation check: compare our computed holdings against actual balances after each sync.
GET /v1/portfolio-history Balances New: balances and performance over time. Could complement or replace parts of our price-backfill-driven portfolio history.
GET /v1/earn/configs Earn (Read) Staking/Earn configurations with APR and availability. Context for reward transactions; not needed for sync itself.
POST /v1/earn/actions/{STAKE|UNSTAKE} Earn (Write) Programmatic staking management. Out of scope for TXLS — we only observe, never trade or stake.
GET /v1/assets any key Assets, currencies and price tickers (replaces /ticker, /currencies).

Staking rewards — how to get them

This was the original question. The answer has three parts:

Works New Public API

GET /v1/operations includes rewards and staking — Bitpanda's own CLI docs describe the operations log as the "full transaction log including rewards and staking", and the migration guide names staking management as a headline feature. The to_eur_rate on trades (and EUR-valued portfolio data) fits our EUR-based model.

Blocked Legacy API

The API we currently call has no rewards endpoint. This is exactly why our sync skips staking rewards today — it's an API limitation, not a missing feature in our sync stack.

Not for us Partner API

techsolutions.bitpanda.com has dedicated staking endpoints (actions with stake/unstake/reward types, staking overview per fiat, non-user-initiated staking_reward transactions) but authenticates with bp-user-id/bearer auth for partner integrations — not usable with end-user API keys.

Recommendation & next steps

Migrate the Bitpanda API client to the new Public API. The legacy base URL dies on 31 January 2027, so this work is required regardless — and doing it once gets us staking rewards for free, eliminating the CSV/manual-entry workaround for rewards.

Implemented Steps 2, 3, 4, 5 and 6 are implemented (commits 8cba58b–a388abb). Step 1 (live-key verification) is now the user's verification step.

Open questions / risks

to resolve in the spike
  • Resolved with live data — a real /v1/operations dump confirmed the type vocabulary: transaction_type is often null on non-trade movements (rewards, deposits, stakes) and the operation_type carries the signal (reward, onetime_reward, stake/unstake, swap, deposit). api-client.ts now falls back to operation_type when transaction_type is absent and skips stake/unstake operations explicitly (tally stakeUnstake).
  • Scope mapping — docs name "Balances" and "Transaction" scopes for portfolio/history; confirm /v1/operations works with "Transaction" alone.
  • History depth — unclear how far back operations data reaches; the sync does a full replace of all transactions, so gaps would surface as holdings drift (which the step-5 reconciliation would catch).
  • Rate limits / pagination limits on the new API — the client caps at 200 pages; re-validate page size and any rate-limit headers.
  • Fiat/other asset classes — operations may include commodity/stock/ETF transactions; assets unknown to /v1/assets are skipped with a warning — check the sync log for unexpected skips.
  • Non-trade EUR values — deposits/withdrawals carry no EUR value from the new API (the legacy API provided amount_eur); rewards get valued from stored daily prices where available.
  • Swap fees — resolved in code + confirmed live: a swap's fee appears on every leg of the trade pair via trade.fee; the client keeps it exactly once (dedup across legs). A swap can also carry a separate fee transaction leg paying the trade fee in kind (e.g. BEST) — that leg is skipped (tally feeLeg). The operation-level fee_amount on rewards is a commission (20% in the live sample) and is deducted from the credited reward quantity, so the app stores the net amount.
  • Pending/corrected operations — the legacy client skipped non-finished entries; the new API exposes no status field. If the first sync contains pending operations, an explicit skip must be added.
  • Hardening done in code (review round 1) — invalid credited_at timestamps are skipped, pagination aborts when has_next_page is true without a cursor, malformed responses throw instead of silently truncating, and a per-reason skip tally is logged after every sync. Still to confirm live: whether the operation-level fee_amount field (currently unread) carries the swap fee — if so, the fee source must move from trade.fee.

Manual verification guide (your part)

user verification
  1. Create the API key. Bitpanda → Account settings → API → create key with the Balances and Transaction scopes (read only — no Trade, no Earn Write).
  2. Probe the real response shapes (replace $KEY): 
    curl -s -H "x-api-key: $KEY" "https://api.public.bitpanda.com/v1/operations?page_size=5" | head -c 4000
curl -s -H "x-api-key: $KEY" "https://api.public.bitpanda.com/v1/operations?page_size=50" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); types=sorted({(str(o.get('operation_type')), str(t.get('transaction_type'))) for o in d.get('data', []) for t in o.get('transactions', [])}); print('\n'.join(map(str, types)))"
    Note the actual operation_type/transaction_type strings — especially for staking rewards, stake and unstake. If any value differs from what api-client.ts maps (buy/sell/deposit/withdrawal/reward/staking_reward/onetime_reward — stake/unstake operations, swap fiat legs and fee legs are deliberately skipped), extend the mapping in server/src/providers/bitpanda/api-client.ts.
  3. Confirm which scope /v1/operations needs — repeat the probe with a key that has only Transaction; if it 403s, add Balances.
  4. Run a sync. Enable API sync on the Bitpanda account (or press "Sync now"), then check the server log for [BitpandaApiClient] skip warnings and the end-of-sync skip tally — every unmapped value shows up there with its reason and count. A separate degradedCounts warning (Degraded transactions imported) lists degraded rows: unparseableTradeNumbers were imported without EUR values (investigate before trusting tax numbers); rewardCommissionMismatch/unparseableRewardCommission rewards were imported with their gross quantity (holdings may slightly overstate until confirmed live). A Duplicate transaction ids were skipped warning reports payload duplicates (first occurrence wins).
  5. Compare results. Pick one recent reward and one recent trade in Bitpanda and check them in the app (transactions list, holdings, tax report): type, quantity, timestamp, and EUR value should match. Note: transactions whose ID already exists in another account of the same user (e.g. legacy CSV imports) are deliberately skipped in this account. Sweep fees: if a real swap reports the fee on both legs, the total imported fee must still equal Bitpanda's single fee (the client deduplicates fees across operation legs).
  6. Check the balance reconciliation. After each sync that imported or replaced transactions the log shows either [ApiSyncService] Balance reconciliation passed or a Balance reconciliation drift detected warning listing per-asset app-vs-Bitpanda quantities. Known false-positive sources: rows of the same Bitpanda account also held in a legacy CSV account (the comparison is per app account, the provider reports the whole Bitpanda account), assets deliberately skipped by the mapper, and portfolio rows that could not be resolved to assets (fiat/goods/BCPEUR rows are expected and only counted in the info log; a Portfolio balances could not be parsed warning fires only for known crypto assets with unparseable balance values). Small drift on assets with long reward histories can be rounding; consistent or large drift points to skipped/unmapped transaction types (see the skip tally above) or API history that does not reach back as far as the app's data — investigate before trusting holdings.
  7. Verify fee/cost-basis semantics on a real trade. The client imports eurValue from rate_with_fee (gross fiat movement) and keeps eurFee from trade.fee separately, matching the legacy CSV's Amount Fiat + Fee columns. Confirm against one real buy/sell that the tax report's cost basis does not count the fee twice (the tax calculator adds eurFee on top of eurValue for buys) and that sell proceeds match Bitpanda's own numbers.
  8. Run the deferred test suites on the host (sandbox had no Docker): integration tests (start the MySQL/Postgres containers first) and all three GUI-test variants, per the AGENTS.md flow.
